# Lane 1 — add `lastmod` to the sitemap entry (2026-08-21)

Item: add `lastmod` to the sitemap entry so AI engines see the edition freshness signal
(research desk 2026-08-20). Branch `lane1/sitemap-lastmod-freshness-2026-08-21`, cut from
`origin/main` at `5b270e4`.

## What was wrong

The sitemap had exactly one entry and no freshness signal:

```xml
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9"><url><loc>https://inish.in/</loc></url></urlset>
```

That single URL is the root page, and the root page is rewritten on every publish. With no
`<lastmod>`, a search or AI crawler sees a byte-identical sitemap on the day a new edition
lands and on a day the site sat still, so the one cheap signal it would use to decide "recrawl
now" was simply absent. Confirmed live before the change:

```
$ curl -fsS https://inish.in/sitemap.xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9"><url><loc>https://inish.in/</loc></url></urlset>
$ curl -fsS https://inish.in/latest.json | head -2   # live edition
{
  "date": "2026-08-20",
```

## What changed

- `scripts/build_daily.py` — `sitemap()` takes the accepted edition and stamps its date:
  `<url><loc>https://inish.in/</loc><lastmod>2026-08-20</lastmod></url>`. The date is
  re-parsed with `dt.date.fromisoformat` (same as `rss()`), so the stamp is the edition's own
  date — the same one the page, the RSS `pubDate`, and `latest.json` publish — not a separate
  hand-maintained value that can drift. Date-only is the W3C Datetime form the sitemap
  protocol allows, and it is the real resolution of a once-a-day edition. `<lastmod>` sits
  after `<loc>`, which is the order the sitemap 0.9 schema's sequence requires.
- `sitemap.xml` — regenerated by running the build against the accepted 2026-08-20 edition.
  The committed root artifacts are what `deploy_daily.sh` ships (it copies the public surface
  out of a pristine `origin/main` snapshot), so the generator change is only real once the
  committed file carries the stamp. `python3 scripts/build_daily.py` rewrote `index.html`,
  `latest.json`, `feed.xml`, and `sitemap.xml`; the build is deterministic, so the only file
  that changed was `sitemap.xml`.
- `tests/test_build_daily.py` — new `test_sitemap_stamps_the_edition_date_as_lastmod` builds
  two different edition dates and pins that the stamp follows the edition, that the document
  parses, that there is exactly one `<url>`, and that its children are `loc` then `lastmod`.
  `test_builds_latest_feed_at_root` also asserts the stamp. `test_committed_surface_matches_the_newest_accepted_edition`
  now covers `sitemap.xml` alongside `latest.json`, `feed.xml`, and `index.html`: the sitemap
  became edition-derived, so a rollover that forgets it would publish a freshness date the
  site no longer has, which is worse than publishing none.
- `tests/test_verify_live.py` — the `SITEMAP` fixture carries a `<lastmod>` so the live-route
  fixture matches the shape actually published.

Nothing else moved. `public-paths.json` already allowlists `/sitemap.xml`, `verify_live.py`
already byte-checks every public path against the snapshot, and `robots.txt` already points
crawlers at the sitemap, so no route, edge, or deploy contract needed a change.

## Operational note (expected, not a defect)

`sitemap.xml` is a published byte-checked asset, so between this merging and the next deploy
the live hostname serves the old un-stamped sitemap and the hourly `Live current check`
workflow will red `LIVE_IS_STALE` on `/sitemap.xml`. That is the designed staleness signal
described in `MEMORY.md`, not a regression: `scripts/deploy_daily.sh` (or the daily publisher
run) ships the accepted `origin/main` surface and clears it. Verify afterwards with
`curl -fsS https://inish.in/sitemap.xml` — it should show `<lastmod>` matching
`curl -fsS https://inish.in/latest.json | jq -r .date`.
